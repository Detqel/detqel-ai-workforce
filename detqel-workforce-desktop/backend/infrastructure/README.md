# Desktop-managed infrastructure

The desktop backend starts an isolated Docker Compose project named `detqel-workforce-<runtime-directory-hash>`. The suffix keeps separate operating-system user profiles from sharing credentials, ports, or named data volumes. Docker Desktop must provide a local Linux engine and Compose v2 or newer. The supported automatic launch mechanism is `docker desktop start --detach`; if that command is unavailable, open Docker Desktop before retrying startup.

LiteLLM uses `docker.litellm.ai/berriai/litellm:latest`. Startup explicitly pulls every required image and stops if a pull fails; it never silently starts an older cached gateway. Creating containers subsequently uses the successfully pulled images without downloading them twice. The Compose asset retains `pull_policy: always` for standalone Compose use. Following `latest` can introduce upstream changes and requires registry access on each application start.

Milvus uses the official standalone v3.0.3 integration with etcd v3.5.25 and its compatible `milvusdb/minio:RELEASE.2024-12-18T13-15-44Z` image. A one-shot container initializes ownership of the Milvus named volume before its unprivileged service starts. PostgreSQL 16 belongs exclusively to LiteLLM; it does not replace or expose the application's primary PostgreSQL database.

Only LiteLLM's container port 4000 and Milvus's container port 19530 are published. Docker allocates available host ports in 50000–59999, bound explicitly to `127.0.0.1`. PostgreSQL, etcd, MinIO, and Milvus management port 9091 have no host publications. Auxiliary services share private internal networks only with their corresponding application service. LiteLLM and Milvus have separate access networks; LiteLLM needs outgoing access to configured model providers. Container listeners use container interfaces, including `0.0.0.0` internally where required; this does not publish those listeners on host interfaces.

The private runtime `infrastructure` directory holds generated credentials and configuration. POSIX directories are restricted to mode 0700; Windows receives a current-user ACL with inherited permissions removed. Generated master keys, PostgreSQL credentials, MinIO credentials, and the Milvus root password persist across starts. The LiteLLM salt key must survive with its PostgreSQL volume because it encrypts stored model-provider credentials. The directory must be backed up with the named volumes. Missing credentials alongside existing project volumes cause startup to stop instead of regenerating secrets. Users with Docker administrator privileges can inspect container configuration; Docker daemon access is a privileged trust boundary.

Runtime startup waits for container health, then verifies authenticated Milvus REST access, LiteLLM database readiness, and LiteLLM master-key access. These are startup checks implemented in the application; no model request is sent. The API endpoints and credentials remain server-side. CLI stderr, container logs, and HTTP response bodies are not included in user-visible errors or progress events. Image downloads have a 30-minute limit, container creation a 15-minute limit, and service readiness shares a 10-minute limit. Cancellation terminates the active CLI child and startup waits without deleting volumes or stopping other projects.

Services use `restart: unless-stopped` and remain running after desktop exit. No shutdown, reset, migration rollback, volume deletion, automatic credential rotation, remote Docker daemon, or Windows-container support is provided by this manager. There is no model configured on first launch. Add models through the authenticated LiteLLM Admin UI or edit the private runtime `litellm.yaml`, which is created only once and preserved on subsequent starts. Find the current gateway host port in the managed Docker project's port mapping and use its `/ui` route; the generated master key is in the private `credentials.json` file. Service image execution and end-to-end startup have not been tested during implementation.
