# Desktop-managed infrastructure

The managed Compose project is `detqel-kin-stack`. It has exactly four services and containers: `detqel-kin-litellm`, `detqel-kin-litellm-db`, `detqel-kin-milvus`, and `detqel-kin-app-db`. The desktop frontend and backend remain native application processes. Docker Desktop must provide a local Linux engine and Compose v2 or newer. These explicit container, network, and volume names identify a single managed stack on the host.

LiteLLM uses `ghcr.io/berriai/litellm:latest`, the publisher's primary registry, and is pulled at each launch. Both `:latest` and `:main-stable` at the previous mirror returned "not found" during desktop startup. The primary registry's `latest` manifest was confirmed available for Linux amd64 and arm64 using public metadata only; no image was run. Image references live in `backend/src/constants/dockerConstants.ts` and are supplied to Compose as required variables. No alternate-image or cached-image fallback is used. Its dedicated PostgreSQL 16 database has no host port and shares an internal network only with LiteLLM. LiteLLM also has a separate network for outbound access to model providers. Its native-backend endpoint is `http://127.0.0.1:<LITELLM_PORT>`.

Milvus v3.0.3 runs as one standalone container with embedded etcd, local object storage, and a local-filesystem Woodpecker WAL. There are no external etcd, MinIO, or initialization services. `milvus.embed-etcd.yaml` binds embedded metadata listeners to the container's loopback interface. Management port 9091 and embedded etcd ports 2379/2380 have no host publications. Its authenticated endpoint is `http://127.0.0.1:<MILVUS_PORT>`.

The application has a separate PostgreSQL 16 container at `127.0.0.1:<APP_DATABASE_PORT>`. Its database name and generated credentials come from `APP_POSTGRES_DB`, `APP_POSTGRES_USER`, and `APP_POSTGRES_PASSWORD`. LiteLLM retains its independent `POSTGRES_USER` and `POSTGRES_PASSWORD` variables. The native backend automatically applies the application's migrations and reference seeds to this managed application database during startup. Existing `backend.env` files, including their `DATABASE_URL` values, remain untouched. The managed application database starts fresh; existing external application data is not copied automatically.

All three published host ports are individual runtime-allocated values supplied through `LITELLM_PORT`, `MILVUS_PORT`, and `APP_DATABASE_PORT`; every publication binds explicitly to `127.0.0.1`. Container listeners can use their container interfaces, including `0.0.0.0` where required, without publishing on the host's external interfaces. New managed Docker networks and persistent volumes have explicit `detqel-kin` names. Containers, networks, and new data volumes carry the private runtime's ownership label.

New named volumes are `detqel-kin-litellm-db-data`, `detqel-kin-milvus-embedded-data`, and `detqel-kin-app-db-data`. The runtime supplies `LITELLM_DATABASE_VOLUME` and ensures that external volume exists before Compose starts; it can select the existing legacy LiteLLM PostgreSQL volume directly, preserving its data and original encryption salt without copying or reinitializing it. This reused LiteLLM volume retains its prior name as the compatibility exception to the new naming convention. Embedded Milvus deliberately uses a fresh volume: existing external-etcd/MinIO Milvus data has a different storage layout and is not mounted or reinterpreted as local data. Previous volumes are preserved. Export/import of legacy vectors requires a separate migration; no automatic vector migration or destructive reset is included in these assets.

The official Milvus v3.0.3 runtime image creates `/var/lib/milvus` for the non-root `milvus` user. The fresh named volume uses Docker's normal population behavior (`nocopy: false`) rather than a host directory created as root; no additional initialization container is required. Existing nonempty volumes with damaged ownership are not modified automatically. The embedded configuration explicitly selects local storage and local Woodpecker files, so it does not inherit the image's external object-storage settings.

Generated service credentials and the Milvus root password persist in the private runtime infrastructure directory. `milvus.user.yaml` substitutes the saved root password and enables authentication; only its local embedded metadata service has authentication disabled. Never regenerate the LiteLLM salt key while retaining its PostgreSQL data: it encrypts stored provider credentials. Back up private configuration and volumes together. Docker daemon administration remains a privileged trust boundary because administrators can inspect container configuration.

Each desktop launch pulls all required images before gracefully stopping and deleting ownership-verified containers from this installation, including the previous `detqel-kin` project. Compose then creates all four containers under `detqel-kin-stack`, including on a first launch with no containers present. A failed download leaves previous containers intact. Persistent volumes, encryption keys, credentials, and private networks survive recreation. Volumes and networks are explicitly external to Compose and created by the startup manager when absent. Unrelated projects are never removed. Containers retain `restart: unless-stopped` between launches.

The native executable serves its loader HTML and logos from an embedded custom protocol. The loader confirms it has painted before native code starts any application service. In development, native code owns the Next.js process and its logs and shutdown; Tauri does not prelaunch or wait for Next.js. Packaged builds load bundled frontend assets without a Next.js server. The loader tracks frontend hydration and IPC readiness, backend process startup, each infrastructure service, application migrations, and backend API readiness. The main window stays hidden until all stages complete. Startup health checks and authenticated service checks do not make model requests. No models are preconfigured: add them through the authenticated LiteLLM Admin UI or the preserved private `litellm.yaml`. No tests, image execution, or end-to-end Docker startup checks were run during this change.
